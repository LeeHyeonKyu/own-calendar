# DB 클라우드 이전 및 백업 체계

PostgreSQL을 클라우드로 이전하고, 홈서버를 백업으로 두는 이중화 구조를 구축한다.

## Problem

현재 PostgreSQL이 홈서버 Docker 컨테이너에서 단일 인스턴스로 운영 중이다. 홈서버 고장, 디스크 손상, 실수로 인한 데이터 삭제 시 일정 데이터가 영구 유실된다. 백업 체계도 없다. PROJECT.md의 "데이터 소유권" 원칙 — 데이터를 소유한다는 것은 안전하게 보존한다는 것도 포함한다.

## Value

데이터 유실 리스크를 제거한다. 클라우드 DB를 primary로 두면 홈서버 장애 시에도 서비스 연속성 확보. 향후 전체 클라우드 전환의 첫 단계이기도 하다.

## Solution

### 단계적 전환

**Phase 1 (즉시): 백업 체계 구축**
- 홈서버 PostgreSQL의 정기 백업 (pg_dump → 외부 저장소)
- 최소 일 1회 자동 백업

**Phase 2: 클라우드 DB 이전**
- 무료 티어 클라우드 PostgreSQL을 primary로 전환
- 홈서버 DB는 백업/복제본으로 유지
- API 서버의 DATABASE_URL만 변경하여 전환

**Phase 3 (향후): 전체 클라우드 전환**
- API 서버도 클라우드로 이전 — 별도 feature (019 앱 패키징과 연계)

### 클라우드 DB 후보 (무료 티어)

| 서비스 | 무료 티어 | PostgreSQL | 특징 |
|--------|----------|------------|------|
| **Supabase** | 500MB, 2 프로젝트 | 15.x | 자동 백업, REST API 내장 |
| **Neon** | 0.5GB, 무제한 프로젝트 | 16.x | 서버리스, 브랜칭 |
| **Railway** | $5 크레딧/월 | 최신 | 간편 배포 |

## Scope

**Includes:**
- Phase 1: pg_dump 자동 백업 스크립트 (일 1회 → 외부 저장소)
- Phase 2: 클라우드 PostgreSQL 세팅 + 데이터 마이그레이션
- DATABASE_URL 전환 (홈서버 → 클라우드)
- 홈서버 DB를 읽기 전용 복제본 또는 정기 동기화 백업으로 유지
- Prisma migration이 클라우드 DB에서 정상 동작 확인

**Excludes:**
- API 서버 클라우드 이전 (향후 별도 feature)
- 실시간 replication (primary-replica 스트리밍) — 가족 규모에서 과도
- 멀티 리전 배포
- 자동 failover (홈서버 → 클라우드 자동 전환)

## User Stories & Acceptance Criteria

### Story 1: 자동 백업

**As a** 현규, **I want** DB가 매일 자동 백업되는 것 **so that** 서버 장애 시에도 데이터를 복구할 수 있다.

**Scenario:**
- Given: 홈서버에서 PostgreSQL이 운영 중
- When: 매일 지정 시각에 자동 백업 실행
- Then: pg_dump 파일이 외부 저장소에 보관된다

**Acceptance Criteria:**
- [ ] cron 기반 일 1회 자동 백업 — verify: 백업 파일 생성 확인
- [ ] 백업 파일이 홈서버 외부에 저장 (클라우드 스토리지 또는 별도 디스크) — verify: 저장 위치 확인
- [ ] 최근 N일분 백업 보관 (오래된 것 자동 삭제) — verify: retention 정책 동작
- [ ] 백업에서 복구 테스트 성공 — verify: pg_restore로 복구 후 데이터 정합성 확인

**Edge Cases & Errors:**
- [ ] 백업 실패 시 알림 (로그 또는 알림) — verify: 의도적 실패 후 알림 확인
- [ ] DB 용량이 커서 백업 시간 초과 — verify: 가족 규모에서는 발생 안 할 것이나 타임아웃 설정

### Story 2: 클라우드 DB 전환

**As a** 현규, **I want** DB를 클라우드로 옮기는 것 **so that** 홈서버 장애와 무관하게 데이터가 안전하다.

**Scenario:**
- Given: 홈서버 DB에 데이터가 있는 상태
- When: 클라우드 PostgreSQL을 세팅하고 데이터 마이그레이션
- Then: API 서버가 클라우드 DB를 바라보고, 기존 데이터가 모두 보존된다

**Acceptance Criteria:**
- [ ] 클라우드 PostgreSQL 인스턴스 생성 (무료 티어) — verify: 접속 확인
- [ ] pg_dump → pg_restore로 데이터 마이그레이션 — verify: 레코드 수 일치
- [ ] Prisma migration 정상 실행 — verify: `prisma migrate deploy` 성공
- [ ] DATABASE_URL 변경 후 API 서버 정상 동작 — verify: CRUD 테스트
- [ ] 홈서버 DB를 백업용으로 유지 (정기 동기화) — verify: 동기화 스크립트 동작

**Edge Cases & Errors:**
- [ ] 클라우드 DB 접속 불가 시 — verify: API 서버 에러 메시지 확인 (홈서버 fallback은 수동)
- [ ] 무료 티어 용량 초과 접근 시 — verify: 용량 모니터링 방법 확인
- [ ] 마이그레이션 중 데이터 정합성 — verify: 마이그레이션 전후 checksum 비교

## Approach

- Phase 1 백업: `pg_dump --format=custom` + cron + 클라우드 스토리지 업로드 (S3 호환 또는 Google Drive)
- Phase 2 전환: 클라우드 DB 선택 후 `pg_dump` → `pg_restore`, `.env`의 `DATABASE_URL` 변경
- 홈서버 백업 동기화: 클라우드 DB를 `pg_dump` → 홈서버에 정기 복원, 또는 클라우드 서비스 자체 백업 활용
- 서비스 중단 최소화: 짧은 maintenance window (수 분) 동안 전환

## Assumptions

- 무료 티어 클라우드 DB가 가족 규모 데이터량과 트래픽을 감당할 것 — if wrong: 유료 플랜 전환 또는 셀프호스팅 유지 + 백업만 강화
- 홈서버 → 클라우드 마이그레이션 시 다운타임을 최소화할 수 있을 것 — if wrong: 사용자 적은 시간대에 전환
